# Operations

How the engine writes, records history, watches, recovers and maintains itself. Crates: `wi-history` (git, manifest, flush, replay), `wi-store` (write path, ingress, watcher, recovery, maintenance), `wi-export` (service), `wi-docs` (import).

## Write path

Every engine write, from the CLI or a `wi_*` tool, runs these steps:

1. Resolve the target path or permalink. Ordinary tools refuse the vault config, generated exports, anything under `.git` and paths outside the vault, and never follow a symlink. Names are compared by file-system identity ([path identity](#path-identity-and-containment)).
2. If the caller gave an operation id, look it up first ([idempotency](#idempotency-and-first-results)). A known id returns its first result before any checksum check.
3. Take the [publisher lock](#publisher-and-manifest). Hash the current file (`old_hash`). If the caller gave an expected checksum and it differs, the write is refused as stale. Reserve the change budget if the operation removes a current claim ([KNOWLEDGE](KNOWLEDGE.md#conflicts-and-the-automatic-change-cap)); the reservation is recorded in the intent.
4. Write a temp file in the same directory and fsync it.
5. Write the new bytes as a git blob and make it durable (object file and directory fsync).
6. Append an `intent` record to the manifest and fsync it.
7. Exchange or rename the temp file into place ([editor race](#editor-race)).
8. Append a `done` record and fsync it. **The write is acknowledged here.** The vault generation advances and the lock is released.
9. Update the index. If this fails, the response carries `index: pending` and the next start repairs the index.
10. Enqueue the commit ([Git history](#git-history-and-sync)). Commits are coalesced and are not part of the acknowledgment.

Steps 4 and 5 run before the lock: the temp file is `<dir>/.<name>.wi-tmp-<pid>-<n>-<nanos>`. The lock is released before the index update. Edits read and transform the note before the lock and require the read hash under it; a concurrent change makes the edit redo itself up to three times unless the caller pinned a checksum.

- Frontmatter edits are byte-preserving ([FORMAT](FORMAT.md#byte-preserving-frontmatter-edits)).
- **Current state.** The current state of a note is the durable working-tree file after fsync, identified by its content hash. It is not HEAD. There is no current-pointer file.
- **Ingress actor.** Each operation records its actor (CLI, MCP, watcher, import, engine, sync) in the manifest and in a commit trailer. The actor is separate from a note's `origin` ([AUTHORITY](AUTHORITY.md#origin-by-ingress)).
- **Crash recovery.** A crash before step 6 leaves the old file and no record. For an `intent` without `done`, startup compares the target's hash: equal to `new_blob` completes the operation with the recorded actor; equal to `old_hash` drops the intent; anything else keeps both versions as a conflict and opens a work item. A refused write changes nothing. A failure after step 8 never undoes the acknowledged file.
- **Multi-file operations** are ordered so that read-time rules keep every intermediate state safe: a supersede writes the successor first; an archive moves the note first, and any note under `archive/` counts as archived whatever its status key; a conflict flag is written to the candidate first.
- **No delete.** Archiving moves a note to `archive/`, keeping its relative path, permalink and history.
- **Missing.** A note deleted outside the engine is detected (by the watcher, a scan or `wi reindex`) and recorded as `missing` in a work item. Its content stays recoverable from git.
- **Engine-owned fields.** A write or edit through `cli` or `mcp` that sets or changes `status`, `adoption`, `check`, `conflict_with`, `origin`, `excluded`, `work`, `deferred`, `work_id`, `work_kind` or `restores` is refused (`restores` is allowed at creation). A replace that omits an existing engine-owned key keeps its value. The agent label `noted_by` is kept the same way, and an MCP edit or replace that removes or changes it is refused (`engine-owned-field`); the owner removes it in a file editor or with `wi adopt`. MCP may not change claim content of a `memory`, `capture` or `work` note, nor change a lifecycle note's `type`: `claim-edit-requires-candidate`.
- **Origin at creation.** A note created through `cli` gets `origin: {kind: user, locator: "cli:write", captured_at}`; through `mcp`, `kind: agent`; through import, `kind: file`. The key is appended byte-preservingly. A change that makes a plain note a lifecycle note is a creation: `origin` comes from the current ingress. A `cli` change of claim content sets `origin.kind=user` and resets a non-candidate memory note to `status: candidate`, as file ingress does.
- **Engine-owned work state.** Write, edit, move, archive and revert through `cli` or `mcp` refuse paths under the work directory (`protected-path`) and any note whose old or new `type` is `work` (`engine-owned-field`). With `lifecycle: on`, a lifecycle note with a future or unparseable `observed_at`, `checked_at` or observation time is refused (`future-timestamp`, `unparseable-timestamp`).
- **Revert.** `wi revert` restores old bytes as a new write. A lifecycle note is refused with `lifecycle-revert-requires-fork`; the lifecycle restores it as a fork with `restores`. A missing file is restored through the creation checks.
- **Locked notes.** `locked: true` refuses every engine write, edit, move and archive.
- **Conflict markers.** A file with `<<<<<<<`, `=======` and `>>>>>>>` at line starts is refused for engine writes; ingress records a `merge-conflict` work request; index hits carry `conflict_markers: true`.
- **Index pending.** A failed index update returns `index: pending` and appends the paths to `.git/wi/index-pending`; the next open or maintenance pass re-indexes them. If repair fails (an unusable cache), the open still succeeds: `OpenReport.index_degraded` and `wi doctor` report it, reads and writes work, and search uses the literal scan. The next CLI command or maintenance pass then rebuilds the index from the files on its own; only if that also fails does the command print one plain warning, and it tries again next time. No manual step is needed. A repair takes the marker by renaming it to `index-pending.claim-<pid>-<n>-<ns>` under the marker lock; writers always append to a fresh marker, and the repair deletes only its claims. Claims left by a stopped repair are taken over by the next one.
- **Generation.** Write results carry `generation` = their `done` sequence id. Reads and searches take the publication state (generation and any open intent) before and after reading and retry once unless both are equal with no intent open; a second inconsistency yields `generation-changed`.
- **Fault hooks.** `WI_FAULT` = `before_intent_fsync`, `after_intent_before_swap`, `after_swap_before_done`, `after_done` abort the process; `index_update` makes the index update fail; `lifecycle_after_candidate` aborts after an adopted candidate is written and before its targets are marked `superseded`. Unset in normal operation.

### Editor race

An editor can save between step 3 and step 7. Where the platform has an atomic exchange (Linux `renameat2` with `RENAME_EXCHANGE`, macOS `renameatx_np` with `RENAME_SWAP`; `NOREPLACE` for creates), the engine swaps the new file in and hashes the displaced bytes. If they differ from `old_hash`, it keeps them as a conflict copy `<dir>/.<name>.wi-conflict-<seq>` with a `conflict-copy` work request, so nothing is lost; a create that loses a race swaps instead and keeps the editor's file the same way. A move takes its source aside as `.<name>.wi-moved-<seq>`, then removes it if unchanged or keeps it as a conflict copy. Where exchange is unsupported (`EINVAL`/`ENOTSUP`/`ENOSYS`, for example exFAT), the engine re-hashes the target, refuses as stale on a change, then renames; the window is best effort. Displaced bytes that matched the precondition are re-hashed through the engine's open handle right before they are unlinked; changed bytes become a conflict copy and the result names it. An editor that writes through a descriptor opened before the swap, after this final check, still loses that write.

| Platform / filesystem | Evidence | Limit |
| --- | --- | --- |
| macOS arm64 / APFS | race tests pass | process crashes tested; power loss untested |
| Linux arm64 / overlay, tmpfs, btrfs | race tests pass in a container | no bare-metal, ext4 or power-loss claim |
| Windows / NTFS | no atomic exchange; re-hash then replace; tests pass on GitHub Actions `windows-latest` | an editor save between the re-hash and the rename can be overwritten ([Windows](#windows)) |
| exFAT | exchange returns `ENOTSUP` | re-hash then rename |

### Idempotency and first results

The operation id is scoped to the vault. The request digest covers the tool, the target and the arguments. The same id with the same digest returns the first result; with a different digest it is refused. The durable record is the manifest record, then the commit trailer `Wi-Operation: <id> <request-digest>`, so it survives restart and index deletion. Across devices the guarantee holds only after sync. A newly encountered merge rebuilds the disposable operation map from every reachable parent; index-free lookup also walks every parent. Loss-event windows likewise include both merge parents once per commit.

A write with an operation id stores `{op_id, request_digest, manifest_id, seq, path, checksum, previous_checksum, conflict_copy, moved_from}` at `.git/wi/ops/<h[..2]>/<h[2..]>.json` (`h` = SHA-256 of the id) after the swap and before `done`. A retry returns these fields with `replayed: true`; `generation` and `index` are current. Lookup order: unretired manifest records, then the stored result when its sequence id is retired in the same manifest epoch, then commit trailers. A result found only in trailers has path, checksum, sequence id, `moved_from` and the conflict copy, but no `previous_checksum`. The device index keeps a disposable table `operation id → commit, digest, seq, path, moved-from` plus the newest scanned commit, so a new id costs one SQLite lookup instead of a walk over every commit.

### Path identity and containment

- **Identity.** Protected names are compared component by component after folding: Unicode NFC, lowercase, NFC again, on every platform. `.GIT`, `.Wiki-Island`, `Exports` or a decomposed `café` are refused wherever `.git`, `.wiki-island`, an export path `exports` or `café` would be. Ordinary note names are not folded: two spellings that alias on APFS are one file to the file system but two paths to git (a limit).
- **Absolute input.** Only the prefix that resolves to the canonical vault root is canonicalized. Components inside the vault are checked as given; an in-vault symlink is refused.
- **Containment.** Every file operation of the write path, reads, ingress and recovery opens directories one component at a time from the root with `O_NOFOLLOW | O_DIRECTORY` and acts relative to that descriptor (`openat`, `renameat`, `unlinkat`). A symlink or non-directory component is refused, and a directory replaced after the check cannot redirect the operation.
- **Windows containment.** The same rule holds without `openat`: each directory is opened one component at a time relative to the previous handle (`NtCreateFile` with a root directory handle, in `wi-sys`), and a symlink, junction or other reparse point at any component is refused. See [Windows](#windows).
- **Persisted paths.** Paths read from the manifest get the same treatment before any read or change. A changed directory leaves outside bytes untouched and records `recovery-problem`.

## Windows

Windows 10 1709 or later on x86_64 (MSVC) with NTFS is the target; the tests run on GitHub Actions `windows-latest` ([VALIDATION](VALIDATION.md#platform)). ARM64 Windows and other volumes (ReFS, FAT, network shares) are untested. All Windows system calls are in the `wi-sys` crate ([DESIGN](DESIGN.md#windows)).

**Mechanisms.**

- **Containment.** Every vault operation opens one component at a time relative to a checked directory handle and refuses a reparse point (symlink, junction) at every component. Before any change, each existing component's on-disk name is read back through its handle and must equal the requested name case-insensitively, so an 8.3 short-name alias is refused.
- **Names.** A vault-relative component with `:`, any of `<>"|?*`, a control character, a reserved device name (`CON`, `PRN`, `AUX`, `NUL`, `COM0`-`COM9`, `LPT0`-`LPT9`, with any extension) or a trailing dot or space is refused. An existing note with such a name (for example synced from a Mac) is never renamed or deleted: it stays in history, is skipped on this device and gets one work request, like any remote name the file system cannot create.
- **Input paths.** `\` is a separator in input and stored vault paths keep `/`. Drive (`C:\`), verbatim (`\\?\C:\`) and UNC prefixes are stripped against the vault root by component, case-insensitively; drive-relative (`C:foo`), root-relative (`\foo`) and device (`\\.\`) inputs are refused. UNC is best effort and unexercised.
- **Rename and delete.** Renames and deletes go through the open handle with POSIX semantics, so a file that another program has open with delete sharing can be replaced or removed. A sharing violation (including access denied on a delete-pending entry) is retried five times with a 20 ms doubling backoff; after that the operation fails without losing bytes and recovery handles it.
- **Placement.** There is no atomic exchange. A replacement re-hashes the target through the checked handle, refuses as stale if it changed, then renames with replace. A create renames without replace and treats an existing file as stale, leaving it untouched. The placement path therefore never makes a conflict copy of a displaced editor file.
- **Processes.** Git transport and document extractors start in a kill-on-close Job Object before they run; a timeout, an output cap or the leader exiting terminates the whole job. If termination cannot unblock an inherited pipe, the wait for the output readers ends after two seconds and the extraction returns an error.
- **Git transport.** Prompts are disabled (`GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, `credential.interactive=never`, a nonexistent askpass program), hooks are pointed at an empty directory under the engine directory, and the 60-second timeout applies as on Unix.
- **Locations.** The data directory is `%LOCALAPPDATA%\wiki-island` (`WI_DATA_DIR` overrides it) and the home folder is `%USERPROFILE%`. The Notion token is a generic Windows Credential Manager entry `wiki-island.notion/<vault id>`; the hidden token prompt turns console echo off and restores it, and refuses when echo cannot be turned off on a console.

**Weaker than Unix.** Each item below is a known difference, not a test gap.

- **Editor race.** The window between the re-hash and the rename can overwrite an editor save made in it. When the target changed before the rename, the write is refused as stale and the editor's file is kept; Unix keeps a conflict copy and succeeds.
- **Namespace durability.** Directories cannot be flushed, so creates, renames and deletes are not claimed to survive power loss as they are with a Unix directory `fsync`. Process-crash recovery is tested; power loss is not measured. `standard` equals `full`.
- **Read-only files.** A path barrier on a read-only file (git objects) cannot open it for writing and records a trace without flushing.
- **Publication renames.** The staged `.git` and folder-mode `git.tmp` publications, the atomic-write temp file of `wi_history::durable` and git's own ref lock files use an ordinary rename, which can fail on a sharing violation where Unix succeeds.
- **Replacing an open file.** A file held open by another program without delete sharing cannot be replaced or removed; the operation fails after the retries.
- **Stray links.** A symlink or junction inside the vault is never followed and is not removed by the engine.
- **Indexing.** Every reparse entry is skipped, including non-link reparse points such as some cloud placeholders. An open SQLite file cannot be deleted on Windows, so an index replacement closes it first. File identity folds the 128-bit file id to 64 bits, which on ReFS can collide.
- **Permissions.** File modes are not carried over; the read-only attribute is the only mode, and private config and backup files rely on inherited ACLs instead of 0600 and 0700.
- **Process identity.** A reused process id can make a dead owner look alive, as on Unix; an unreadable process counts as alive.
- **Service.** The background service is a per-user Task Scheduler logon task ([Service](#windows-task-scheduler)).
- **Creation flags.** A job-started child cannot carry custom process creation flags.
- **Tools.** Benchmarks report machine details and Python-based process metrics as unknown.

## Git history and sync

- Commits are coalesced in an in-process queue: flushed in batches off the hot path, one commit per acknowledged operation, one per bulk import. The queue flushes on exit, including a one-shot CLI exit.
- The watcher commits external editor changes after a debounce. On Linux it expands directory events into file ingress using the vault's ignore rules, without following symlinks.
- `wi commit` commits pending changes by hand.
- **Pending manifest.** Until a commit covers it, every acknowledged engine save is recoverable from its git blob and manifest record. Startup replays the manifest before it accepts writes: it settles open intents, commits each uncommitted `done` record, then publishes remaining external changes as watcher ingress.
- **Limit.** Intermediate external-editor saves the engine never saw are not preserved.
- Revert never rewrites history. It is a new commit that restores earlier bytes; for a lifecycle note it is a new note with `restores` that runs the gates again.
- `wi history` and `wi revert`, and MCP `wi_history` and `wi_revert`, show a note's git log and run revert. Renames are not followed: history of a moved note is under its old path. `wi_history` checks that its target exists and is readable without reading the file (`Vault::require_readable`), so it also works for a file above `max_note_bytes`.
- An error about a host settings file, from `wi mcp install` or `wi setup`, names the file by file name only and never echoes its contents or absolute path.
- `wi sync setup <url>` remembers a remote address locally without contacting it; `wi sync status` reads local retry state; `wi sync [--json]` explicitly synchronizes git-mode vaults. The remote's advertised default branch is used. An empty local remote keeps its symbolic default branch; other empty remotes start with `main`. Folder mode refuses git remote transport. Populated engine remotes must carry the same `vault_id`; a mismatched vault is refused before publishing either side. The index is never synced.
- Sync first excludes files above 50 MiB, takes in editor changes and flushes. It fetches through system git with explicit git directory and working tree, terminal prompts disabled, SSH batch mode and a 60-second timeout per subprocess. Transport holds no engine locks. Startup retires transport scratch and temporary fetch refs from dead owners, in chunks of at most 256 files per directory. Local application then takes the flush lock followed by the publisher lock and refuses to apply over new pending saves or changed files.
- A fast-forward applies exact remote bytes. A divergence compares each path to the merge base: unchanged sides yield to changed sides; identical edits coalesce; conflicting edits retain the local path and put remote bytes in the committed sibling `.<name>.wi-conflict-sync-<remote-prefix>`; copies are readable by path and excluded from note indexing and lifecycle adoption. The conflict-copy work request is recorded on the merging device; other devices receive the committed copy, `wi doctor` lists it there as an `ok` `sync-conflict-copies` line rather than a warning, and its work item appears read-only (`actionable: false`) after the merging device converts the request and syncs. A local deletion keeps the remote edit in a copy; a remote deletion keeps the local edit and records a conflict request. Merge commits have local history as first parent. No force push, history rewrite or conflict markers. A remote path this device's file system cannot create (a name too long for it, or one it rejects) is skipped here with one work request: it stays in history and on other devices, is never recorded as a deletion (by the watcher, a scan, `reconcile` or a later sync), and the rest of sync goes on. File names longer than 224 bytes count as not creatable, which leaves room for sibling names. A conflict copy of a long note name is shortened at a character boundary and ends in `~<8 hex>` of the full name, so it always stays creatable and visible.
- Before modifying files, fetched objects and a sync intent are barriered. Descriptor-relative staged files preserve displaced editor bytes. A working file that holds neither the expected old nor the planned bytes (an editor saved it after the intent was prepared) is never swapped out: it stays visible and is saved as a follow-up local change after the ref advances, so the planned version stays in history one commit below it (`kept_local` in the sync report). Startup replays the intent before ordinary manifest recovery: finish files, record conflict-copy work requests, CAS-publish and barrier the ref, advance the manifest checkpoint generation, update the device index, then remove the intent durably. A busy git staging index does not hold canonical publication open; ordinary flush/recovery retries that disposable refresh. Publishers and flushers wait for replay after an interrupted sync. Reads treat a pending sync as an open publication. Note bytes, including origin and agent labels, stay unchanged. If another git tool moved the branch meanwhile, replay retains the planned version under an immutable recovery ref, leaves the newer branch in place and records review work; the next sync can retry.
- The service runs sync on a separate thread at startup, about 60 seconds after publications settle, and every five minutes. Maintenance and MCP never run transport. Failures persist exponential backoff from one minute to one hour. After 24 continuous failing hours the background thread emits one plain health line; success resets it.
- **Large files.** No path adds a file above 50 MiB to history, in either storage mode and with or without a remote. Watcher and CLI ingress check the size before hashing; an engine write (capture, `wi write`, import) of such bytes places the file in the folder without a blob, intent or commit. In every case a managed `info/exclude` line and one work request are made durable first, so a later ingest cannot commit the file. When the file shrinks back to 50 MiB or less, ingest of the path (and every `reconcile` and sync) lifts its managed rule, so the note is ingested and synced again. An oversized engine write with an operation id stores its first result, so a retry replays it; an editor save to the file it displaces is kept as a conflict copy, as on the ordinary write path. History keeps any earlier version of the path as is: a tracked note that grows past 50 MiB keeps its last committed version at the tip, so sync never deletes it on another device, and the new bytes stay on this device. A large blob already committed by another tool stays in local history; an outgoing-history size guard refuses its upload, preserves local history and records review work, and sync never rewrites that history.
- **Network.** Transport runs only in `wi sync`, `wi publish`, the background sync and publish threads and the explicit `wi setup --github` (it asks the hosting service, through the GitHub CLI, for the account name and finds or creates the private repository), never while an engine lock is held; capture, search, read, maintenance and MCP never use the network. `wi sync setup <url>` only stores the remote address locally.
- **Externally written conflict markers.** A note left with conflict markers gets the `conflict` flag and a work item. The engine does not write into that file. The owner resolves it in any editor, and the next commit clears it.
- Never put `.git` inside an iCloud Drive or Google Drive folder ([DESIGN](DESIGN.md#storage-and-history)).

## Publisher and manifest

- **One publisher per vault.** A short OS advisory lock on a file inside `.git` (`.git/wi/publish.lock`) serializes publishing. It is held only from the budget reservation through the manifest records (steps 3-8), never across a model or network call.
- **Files** in `.git/wi/`: `manifest.log`, `publish.lock`, `flush.lock` (serializes flush, replay and revert), `quarantine/<time_ms>-<offset>.bin`, `ops/`, `work-requests.jsonl`, `index-pending`, `git-index-pending`, `watcher-lease`.
- **Framing.** The manifest starts with the line `wi-manifest 1`. Each frame is a little-endian `u32` payload length, the first 8 bytes of SHA-256 of the payload, then one JSON record. Every append is one write followed by a file barrier.
- **Records.** `checkpoint {manifest_id, next_seq, generation, retired_upto}` is always first. `intent {seq, op_id?, request_digest, actor, path, moved_from?, old_hash?, new_hash, new_blob, revert_of?, batch?, losses?, time_ms}`, `done {seq}`, `ingest {seq, actor, path, new_hash, new_blob, batch?}`, `abort {seq}`, `conflict {seq, current_hash}` and `conflict_ack {seq}`. Hashes are `sha256:<hex>`; `new_blob` is the git blob id. Open intents have disjoint paths; an `intent` or `ingest` on a path an open intent changes is refused.
- **Blob before record.** `Blob::write_durable` barriers the loose object, its fan-out directory and the objects directory; an append refuses a blob id the object database lacks.
- **Retirement** rewrites the log atomically (temp file, barrier, rename, directory barrier) as a new checkpoint plus the byte-identical frames of later records. The manifest id is random, so sequence ids never collide across devices.
- **Sequence high-water mark.** A sequence id is never handed out twice within one manifest id. Quarantine does not roll `next_seq` back; gaps are harmless.
- **Corrupt tail.** A record that fails its frame or checksum, and everything after it, is moved to a quarantine file inside `.git` (durable first), and a work item is opened. Nothing is silently dropped.
- **Generation.** Every publish advances the vault generation, the sequence id of the last published record; it survives retirement.
- **Committed-record check.** A record counts as already committed only when the commit naming its sequence id also holds it (`Wi-Actor` or `Wi-Batch` matches and each path effect is visible in the commit tree or superseded by a later record). Otherwise the flush stops with `CommittedMismatch`.
- **Commits.** Each carries `Wi-Seq: <seqs> <manifest-id>`, `Wi-Actor`, and when present `Wi-Operation`, `Wi-Batch`, `Wi-Moved-From`, `Wi-Revert` and one `Wi-Loss: <json>` per charged loss event (`{at, target, entities, kind, actor}`). The branch moves only by compare-and-swap from the parent the flush built on; a moved branch fails the flush with nothing forced or retired. After a commit the git index is rewritten from the new tree (best effort) so a manual `git commit` keeps engine files.
- **Flush stops** at an open intent, an unacknowledged conflict, a `CommittedMismatch`, or the first record of a bulk batch whose `last` record is not yet appended; it retires only the prefix whose records are all committed or settled. A batch commits as one commit at the position of its `last` record; records interleaved with it commit first as their own commits. The tree after the last commit equals applying every record in manifest order.
- **Replay** order: quarantine a frame that fails its length, checksum, decoding or ordering check together with everything after it; settle the open intent through a `WorkingTree` hash; flush. A conflict blocks the flush until `Manifest::ack_conflict`.
- **Revert.** `History::revert` flushes first and then, holding the publisher lock through the ref update, refuses with `PendingFlush` while any record is left.
- **Limits.** An import that dies mid-batch blocks the flush until a record with the same batch id and `last: true` is appended. Power loss is not simulated; crash tests kill the process, and barrier order is asserted on an in-process trace.

### Durability modes

Vault config key `durability`, `"standard"` (default) or `"full"`; `Vault::with_durability` overrides it. An unknown value or unreadable config fails `Vault::open` with `InvalidConfig`. Every barrier goes through `wi_history::durable::{barrier, barrier_dir}`; the workspace `clippy.toml` disallows direct `File::sync_all` and `File::sync_data`.

- `standard`: POSIX `fsync` on files and directories. On Apple platforms it orders writes and survives process and OS crashes but may not survive power loss, because the drive cache is not flushed. This follows Apple's `fsync(2)` and `fcntl(2)` man pages; it is not measured here.
- `full`: `F_FULLFSYNC` on Apple platforms, falling back to `fsync` only where unsupported; `fsync` elsewhere.

Ordering rules are identical in both modes. On Windows the two modes are the same: files are flushed with `FlushFileBuffers` on a write-capable handle and directory barriers do nothing ([Windows](#windows)).

### Barrier order

- **Save:** blob object, its fan-out directory and `objects/` → manifest `intent` append → working-tree write → `done` append.
- **Flush, per commit:** commit object, root tree, and every tree and blob along each changed path (including the path a move removed) → ref update → ref file and every directory up to `.git/refs` → retirement.
- **Flush of already-committed records:** the commits holding them, along their paths, and the ref again → retirement. A visible ref is not proof that its barrier completed.
- **Init:** the repository is built in `.wiki-island-init.tmp/`; every file and directory of its `.git` passes the barrier; then `.git` is renamed into the vault root. Opening then barriers the root and only afterwards writes `.git/wi/init-complete`. An absent marker makes the next open or init redo the root barrier before any write. In folder mode the same sequence runs in the data directory: `vaults/<vault_id>/git.tmp/` is barriered, renamed to `git`, and opening barriers `vaults/<vault_id>/` before writing `git/wi/init-complete`. Paths written `.git/wi/...` in this document are `<git dir>/wi/...` in folder mode.
- **Quarantine:** quarantine file and directory → manifest rewrite.

Setup records absolute host configuration paths, skill directories, the setup home and cache root in `targets.json` in the per-device local directory (`.wiki-island/local/` in git mode, `<data_dir>/wiki-island/vaults/<vault_id>/local/` in folder mode; operations on an opened vault use that vault's own local directory, so an explicit data directory keeps this state there, and path-only commands use this device's default data directory); automatic skill sync and uninstall use those recorded destinations, and the service sets that home explicitly. Existing vault notes and index rebuilds are unaffected; installations without recorded destinations skip automatic host writes until setup records them.

Rule exports share a device-local digest and refresh after watcher maintenance, MCP background work and `wi maintain`; unchanged rules do not cause publications. Log rotation failures warn once per watcher and leave background care running. Doctor counts ready work items as tasks for the AI; maintenance reports the same count in its summary and `tasks_ready` result field.

## Watcher

The watcher runs inside the MCP server, `wi watch` or the service. Nothing requires it.

- **Ready versus catch-up.** "Ready" (≤ 300 ms) means usable with no vault scan. Before answering, a one-shot CLI query runs a stat-walk catch-up: a directory walk that hashes a file only when its stat data changed.
- The MCP server answers `initialize` before any vault scan: reconciliation, the stat catch-up and rules-export regeneration run on its background thread. Until they finish, results carry the older `index_as_of`, and a current read may report `generation-changed` while startup publications touch its dependency set; clients retry only that diagnostic.
- **Correlation.** The watcher ignores an event whose path and hash match an in-flight (`intent`) or `done` manifest record, comparing the file's git blob id with the newest manifest record for the path, else with the blob at the branch tip. The comparison runs under the publisher lock, so an event that arrives during an engine write waits for `done`. Only an unmatched change is file ingress: the watcher publishes it as an `ingest` record (blob first, actor `watcher`).
- `notify` through `notify-debouncer-mini`, debounce `watch_debounce_ms` (default 200 ms). The watcher thread opens its own vault handle. Each debounced batch is ingested, indexed and flushed. Engine scratch files, `.git`, `.wiki-island/local`, `.obsidian/`, `.trash/`, `.gitignore` matches and `<git dir>/info/exclude` matches are skipped. The exclude file has the lowest priority: a `.ignore` or `.gitignore` rule that re-includes a path wins, in single-path ingress and in every walk alike. A directory is matched with directory semantics before it is read, so an ignored directory, even an unreadable one, is pruned without an error. `wi commit` runs the same ingress over the whole vault (`reconcile`) and records tracked files missing from the working tree.
- **Order and retry.** `wi watch` starts the watcher first, then runs `reconcile` and `flush` while events queue, then enters the loop, so a change during start-up is not lost. When a flush fails, the watcher keeps a dirty flag and retries every 5 s, and keeps the shutdown flush.
- **Repair scan.** The watcher runs a stat-scoped repair scan at start, every 30 s, and within 1 s (coalesced) after a backend error or a skipped directory event, so a save the event stream missed still reaches history. A repair succeeds only when the scan reports no failed paths; otherwise the lease is withdrawn and a retry follows after `min(30 s, 5 s)`.
- **Lease.** A running watcher writes `.git/wi/watcher-lease` (magic, pid, host name, heartbeat in ms, per-watcher token), refreshed every 2 s and removed on stop only when the token is its own. While a lease is held, `auto_ingest` returns an empty report, so one-shot commands skip the stat scan. A lease counts as held only when the host name matches, the heartbeat is within 10 s and the pid is alive. The 2 s, 10 s, 30 s and 5 s values are unmeasured policy choices.
- Results carry `index_as_of`. A current read re-verifies the file hash of each returned hit (at most 8) and re-reads or withholds on a mismatch.
- **Ingress on lifecycle notes.** A `memory`, `capture` or `work` note without `origin` and without `noted_by: agent` that is new, changed in claim content or had its agent label removed gets `origin.kind=user`; a written `origin` is kept as written ([AUTHORITY](AUTHORITY.md#origin-by-ingress)). A claim-content change resets a `memory` note's `status` to `candidate`. This is an engine write recorded after the `ingest`; the gates then run.
- **Hooks.** `Vault::watch_with_hooks(tuning, WatchHooks { on_maintained })` lets the CLI react to a maintenance pass; the older watch APIs remain.

## Index rebuild and fallback

- `wi reindex` rebuilds the device index from files. Deleting the index loses nothing; file-first writes leave no state that files cannot rebuild.
- If the index is missing or corrupt, search uses a literal file scan; those hits are labelled `fallback`. A change of the index schema version rebuilds it on open, and maintenance rebuilds it on detected drift.
- **Sliced rebuild.** A maintenance pass with a time budget (the watcher's) rebuilds an unusable index, one without a complete walk, or one whose pending repair failed in chunks of 128 files (an unmeasured policy value), checking the budget after each chunk, so a slice exceeds its budget by at most one chunk. The first step deletes `index_as_of` and writes the `index_meta` row `rebuild_after` in one transaction; each chunk force-parses its paths in path order and commits its rows, its `skipped` and `diagnostics` entries and the new `rebuild_after` in one transaction, so a crash keeps the previous or the new progress. A stopped pass reports `complete: false` with its cursor at the index stage, and the next pass, in this process or a new one, resumes after `rebuild_after`. The last slice stat-compares every file with its row (catching edits to paths rebuilt earlier), removes rows of files gone, resolves links, then writes `index_as_of` and deletes `rebuild_after`; claimed pending paths are re-read and missing notes recorded, as after `wi reindex`. Until then `index_as_of` stays empty: search answers from the labelled literal scan, MCP's first ranked query may finish the walk with its one foreground catch-up, and `wi doctor` reports `rebuild in progress`. Watcher and write-path index updates keep landing on the partial index meanwhile. A pass without a budget (`wi maintain`), `wi reindex` and the CLI's degraded-index rebuild still rebuild in one step; any complete walk ends an unfinished sliced rebuild. Deleting the index or a schema-version change drops the progress, and the rebuild starts again. Existing vaults keep working: no note format, protocol or index table changes, and progress counts only while `index_as_of` is absent.
- The `lifecycle_snapshots` table holds one row per lifecycle note: the indexed content hash, a format tag (`note-snapshot/1/<crate version>`) and the parsed snapshot. A row with another format tag is ignored, so a binary that parses differently re-reads the files until the index is rebuilt.

## Maintenance

`Vault::maintain(&MaintainOptions { full, time_budget }) -> MaintainReport` ([KNOWLEDGE](KNOWLEDGE.md#self-maintenance) lists what a pass does). `MaintainReport` is serializable: `repaired`, `index_rebuilt`, `work_created`, `work_closed`, `procedures_changed`, `migrated`, `elapsed_ms`, `complete`. A pass is idempotent and deterministic, commits nothing and writes nothing when nothing changed, and calls no model or network. It also moves work notes from an older layout into `.wiki-island/` once (`migrated`); existing captures stay where they are. Archiving honors the configured `archive_dir`. Notes under the default `archive/` folder or any previously configured archive directory remain archived when `archive_dir` changes. A pass records the vault generation and redoes scan input that becomes stale. It publishes at most one commit for all work-item changes and the built-in procedure refresh. Host-config backups taken by `wi setup` live in `backups/` of the per-device local directory. `write_attachment` and every import write refuse `.wiki-island` and `.git` at any depth.

- `wi maintain [--full] [--json]` runs one pass now (`--full` also compares every file with the index).
- **Primary device (folder mode).** Only the device named by `primary_device` runs the stages that write shared notes: the work-note migration, the built-in procedure refresh and every lifecycle stage (work-request conversion included). Other devices run recovery, index repair and procedure change detection; their own work requests stay per-device requests, listed by `wi doctor` on that device. `wi setup --primary` takes over. Git mode has no primary: every clone maintains its own history.
- **Cleanup.** A pass removes engine temp files whose writer process is dead and that no open intent or recovery problem references; they hold only engine bytes nobody acknowledged. It closes any work item whose cause is gone, for example a gate item for a note that became active, and a recheck for a request already converted.
- **Owner deletes and renames.** A delete or rename made in an editor or Obsidian is committed automatically as an owner action; no recheck work item is opened for it.
- **Schedule.** The watcher runs a pass after its first repair, then only when the vault generation changed since the last pass, at most once per 15 minutes (`WatchTuning::maintain_interval`), plus one full pass per 24 hours (`full_maintain_interval`). Idle cost is one generation check. A pass runs on the watcher thread between events with a time budget (default 2 s per slice) and resumes on the next tick. No new daemon.
- Skills sync does not depend on maintenance: it is driven by a persisted digest that the watcher, the MCP server and the CLI each compare ([INTEGRATIONS](INTEGRATIONS.md#skills-export)). The MCP server also notices when the index file was replaced and reopens it.

## Work items

A work item is a `type: work` note under `.wiki-island/work/<device_id>/` with `work: {target, state, next_action, next_trigger, outcome, reason, limits, reopen}` ([FORMAT](FORMAT.md#status-sets)).

- States: `ready` → `investigating` → `checkpointed` → `closed`.
- Closed outcomes: `adopted`, `narrowed`, `alternative`, `not_supported`, `evidence_unavailable`, `closed_without_supported_answer`.
- Every outcome except `adopted`, `narrowed` and `alternative` needs `limits` and a concrete `reopen` trigger. A failed or unsupported result stays visible as unresolved and never counts as success.
- A stop for time or budget alone is `checkpointed`, never `closed`.
- Triggers: `session` (start or end), `source-change`, `query` (a miss), `cooldown`. An empty pass writes nothing.
- Sources: pending captures, failed or undecidable gates, conflicts, invalid `supersedes` targets, drift rechecks, ingest failures, `missing` notes, merge conflicts, recovery conflicts, quarantined manifest tails, deferred capped changes and procedure health problems. Maintenance closes an item automatically when its cause is gone.
- `wi work list|close|open-conflict` and `wi_work` (`list`, `open`, `close`, `sweep`, `next`) list, open and close items; a close that lacks the required limits or reopen trigger is refused (`work-close-refused`).
- Listings include an `actionable` flag: only this device's items enter `wi_work next`, closure, deferred execution and lifecycle updates; other devices' items remain readable. Flat work notes migrate on open through the normal move protocol, with index repair marked before the move.
- Per-device requests in `.git/wi/work-requests.jsonl` (deduplicated by kind, path and detail): `conflict-copy`, `recovery-conflict`, `recovery-problem`, `merge-conflict`, `missing`, `quarantine`, `ingest-failed`, `gate`. Every device can turn its own requests into namespaced work notes, including non-primary folder-mode devices.

## Attachments

Originals stay inside the git repository by default and import never modifies them. For attachments above an unmeasured 20 MiB threshold, `wi doctor` warns and recommends considering Git LFS. LFS setup is never automatic. A hash folder outside git is not provided: it needs another backup and sync contract.

## Read limit and CLI errors

- **Read limit.** `wi read` and every tool that delivers a file a caller named refuse a file above `max_note_bytes` (default 8 MiB) without reading it; the rules and the list of what is bounded are in [PROTOCOL](PROTOCOL.md#read-limit-and-query-cap). The CLI prints `<note path> is larger than the read limit. Open it in its own app, or raise max_note_bytes in .wiki-island/config.toml.`, reports the code `too-large` with `--json` and exits 1. Reads inside the write path, recovery, ingest, import, publish and maintenance still load whole files.
- **Query cap.** `wi search` with a text or title query above 2048 bytes or 64 terms prints `The search text is too long. Search for a few key words instead.`, reports `invalid-request` with `--json` and exits 1. Exit 2 stays reserved for usage errors.
- **Plain errors.** Every error the CLI prints is one or two plain sentences with the next step. It never prints an absolute filesystem path, the text of an operating-system error, an error chain, a type name or engine jargon. A path inside the notes folder is shown relative to it and any other path by its file name. An I/O error has its own sentence for permission denied, storage full (also quota exceeded), file not found and every other case. Installer, service, document-import, lifecycle and note-parsing errors keep their own plain message; any other error prints `Something went wrong and wi could not finish. Run wi doctor to check your notes folder.` With `--json` the error object keeps exactly `code`, `message` and `hint`.
- **`WI_DEBUG`.** With `WI_DEBUG=1` the CLI also writes the full original error chain to standard error on a separate line that starts with `detail: `. Without it nothing internal is printed. The installer for Windows reads the same variable ([Install and release](#install-and-release)).
- **Compatibility.** No format, config or index-schema change. The only change to an existing error code is that an over-cap query reports `invalid-request` instead of `index`.

## Document import

`wi import` prints the reason for each failed file in its human output.

`wi import <path>... [--ocr auto|off|required] [--json]` accepts files and directories; for a Notion ZIP or folder export an absolute path outside the vault is allowed (read-only source, converted copy written into the vault). It reads existing vault-relative originals through the contained store reader, extracts locally, checks the source checksum again, and ingests the original bytes with actor `import`. It publishes the run note before the sidecar, each through the expected-checksum write path; the run snapshot lets a retry complete a missing sidecar. A Notion export ([FORMAT](FORMAT.md#notion-exports)) is converted into notes by the same command.

- A CLI invocation, or library `import_many`, uses batch marks for one commit containing all successful publications; `.git/wi/import.lock` serializes import batches. After interruption, recovery settles any open intent and closes abandoned `wi-import-` batches. A retry can make additional commits after a stopped partial batch.
- Partial per-file failures are reported; other inputs continue, acknowledged output is committed, and the command exits nonzero if any import failed. `wi import <dir>` continues past an unreadable subdirectory or non-UTF-8 name, reporting each as a coded entry, and skips files matched by the vault's ignore rules; explicitly named ignored files report failure.
- Existing hand-enriched sidecars or inconsistent provenance cause a conflict; move the note aside to import a fresh projection.
- `Off` never invokes OCR. `Auto` and `Required` use an existing local Tesseract for supported images and PDF pages via local `pdftoppm`; unmet OCR is a reported `needs_ocr` state, never an installation or network operation. PDF pages without extractable native text first try local `pdftotext -layout`, even with `Off`, then rasterization and OCR when enabled. OCR uses `kor+eng` when Korean traineddata exists, otherwise `eng`. Models, VLMs and macOS Vision are not used.
- **Tool discovery** is tri-state: present (with version), absent (spawn `NotFound`) or unknown (probe timeout, budget, any other probe error). Present and absent are part of the cache identity and final; unknown is transient, retried on the next import, and its cause appears in the run diagnostics.
- **Timeouts.** Each external extraction tool runs in its own process group (on Windows, in a kill-on-close Job Object) with a 60 s timeout per call (`WI_TOOL_TIMEOUT_MS`) and an output cap; a timeout or cap kill stops its descendants too. Each document has a total budget (`WI_IMPORT_BUDGET_MS`). A run that ended `partial` from a timeout or the budget, or `needs_ocr`, is re-extracted on the next import; if the retry fails, the prior original/run pair stays intact. Permanent results are reused from the cache.
- **Safety bounds** (unmeasured): a 256 MiB source-size preflight; both derived notes must fit `max_note_bytes` (oversized output keeps a whole-page prefix, status `partial`, `pages_not_indexed`); CSV records parse incrementally and stop at the logical-page text bound. These are not a hard process memory limit.

## Zero-maintenance operations

Nothing here puts a daemon, network or model on the capture or search path.

- **Auto-ingest on one-shot commands.** Opening a vault for any `wi` command except `init`, `mcp` and `note` first runs `Vault::auto_ingest`, a stat-scoped reconcile: it ingests (actor `user`) the paths whose stat changed since the last walk and that the engine has not recorded, without hashing unchanged files. The command then flushes before it returns success. A flush failure is returned as an error; if the command itself failed, the flush is still attempted and the command error is reported first. `Vault::open` and MCP `initialize` do not auto-ingest. Cost is O(number of paths): tens of milliseconds at 10,000 notes with nothing changed; a missing cache costs a one-time full compare ([PERFORMANCE](PERFORMANCE.md#targets)).
- **Ingress-stat cache.** The baseline is a disposable per-device file next to the index cache, keyed by vault id. A stamp is written only after a file's bytes were matched to the manifest or HEAD, or ingested. A missing or invalid cache, or a HEAD change not made by the cache owner, compares the affected paths against history. Every ingress-eligible regular file is covered, attachments included. Deleting the cache loses nothing.
- **Limit.** A change that preserves size, mtime, ctime and inode is detected only by the full compare: `wi commit`, `wi watch` start, or `wi doctor`.
- **Per-path ingest failures.** `auto_ingest` and `reconcile` do not stop at the first failing path. Each failure goes into `ReconcileReport.failed`, gets an `ingest-failed` work request and is not stamped, so the next run retries it; every other path is still ingested and committed. The CLI prints `warning: <path> is not in history yet: <error>` for each and keeps its exit status.
- **Deletion bookkeeping.** Every successful engine publication is recorded, and `Vault::flush` then re-stamps those paths whether or not the flush succeeds, re-checking the file against the manifest and its stat. A file the engine wrote is not hashed again, and deleting it later is recorded as `missing`. When the branch tip moved or no cache exists, the survey adds every tip-tree path absent from the working tree to the deleted set.
- **Doctor `unseen`.** `wi doctor` reports `unseen`: `ok` when no ingress-eligible file is unrecorded, otherwise `warn` with the count. Files that cannot be read produce a separate `warn` with the count and the first 5 paths.
- **First index walk at init.** `wi init` records a completed first walk, so a fresh vault does not answer from the literal fallback.
- **MCP first query.** When the index has no complete walk, the first `wi_search`, `wi_list`, `wi_find` or `wi_context` call runs one foreground catch-up; later calls do not. A failed catch-up stays retryable and the literal fallback answers meanwhile. `initialize` performs no scan.
- **Warnings.** CLI `--json` object outputs carry a `warnings` array for ingest failures that did not stop the command. Array outputs keep their original shape; nonempty warnings go to stderr as one compact JSON line `{"warnings":[...]}`.
- `wi watch --json` writes newline-delimited JSON, one event per line.

## Service

`wi service install|uninstall|status` manages an optional per-vault background service that runs `wi watch` (watcher, maintenance, and the sync and Notion publish threads when configured on this device): a launchd LaunchAgent on macOS, a systemd user unit on Linux and a Task Scheduler logon task on Windows. `wi setup` and `wi uninstall` call the same code. On other targets install returns an unsupported error and `wi setup` skips the service. No capture or search path depends on the service.

### macOS (launchd)

- Label `com.wiki-island.watch.<vault_id>`. Plist `$HOME/Library/LaunchAgents/<label>.plist` with `ProgramArguments` `[<absolute wi binary>, "watch", "--vault", <absolute vault root>]`, `RunAtLoad` and `KeepAlive` true, `ProcessType` Background, stdout and stderr to `$HOME/Library/Logs/wiki-island/<vault_id>.log` (only changes and errors are logged; the file rotates at 1 MiB and one old file is kept), and a fixed `PATH`.
- `service install` without `--yes` prints a diff. Applying writes the plist atomically, backs up a differing existing file under a unique name, rejects a symlink or non-regular destination, refuses a stale preview, creates the log directory, runs `launchctl bootout` (only a recognized not-loaded result is ignored) and then `launchctl bootstrap gui/<uid>`. A bootstrap failure rolls the change back. Other launchctl failures are reported. Paths are XML-escaped and must be absolute and exist.
- `status` reports label, installed, loaded and the plist and log paths. Tests use a fake launchctl (`WI_LAUNCHCTL`) and a temporary HOME.

### Linux (systemd user unit)

- Unit `wiki-island-<vault_id>.service` in `$XDG_CONFIG_HOME/systemd/user` (an unset or relative `XDG_CONFIG_HOME` means `~/.config`). The first line is exactly `# Managed by wiki-island. Vault <vault_id>.`; it marks the unit as owned. `ExecStart` runs `<absolute wi binary> watch --vault <absolute vault root>`. The program path is double-quoted with `%` doubled; systemd does not substitute `$` there, and it refuses program paths with `"` or `\`, so planning rejects such a binary path with one sentence. The other words are double-quoted with `\` and `"` escaped and `$` and `%` doubled so paths stay literal; `Environment="HOME=<home>"` (`%` doubled); `Restart=always`, `RestartSec=5`; `WantedBy=default.target`. Output goes to the user journal; there is no log file to rotate.
- A user manager is usable when `systemctl --user show-environment` exits 0; its output is never shown. Every call runs `systemctl --user` (`WI_SYSTEMCTL` replaces the executable; tests use a fake).
- A regular file with the unit's name whose first line is not the marker belongs to someone else. Planning, applying and uninstalling refuse it without any systemctl call: "A different service unit named wiki-island-<vault_id>.service already exists; rename or remove it, then run wi setup again".
- Applying records the prior file and reads `is-enabled` and `is-active` from their standard output (`enabled`, `disabled`, `static`, `not-found`, ... and `active`, `inactive`, `failed`, `activating`, ...). A failed call or an unknown answer stops apply before anything changes. It then writes the unit with the same backup, symlink and stale checks as the plist, then runs `daemon-reload`, `enable`, and `restart` when the content changed or the unit was active, otherwise `start`. An identical unit that is enabled and active is left alone. Any failure restores the prior file (or removes a new one), reloads, and restores the prior enablement and running state; the first error is reported. A unit with the vault's name that is running without a unit file, and that no recorded install of this vault explains, is not ours: apply stops after the two probes with "A different service unit named wiki-island-<vault_id>.service is running without a unit file wiki-island knows; stop it, then run wi setup again".
- Before applying changes a unit, it records the unit path in the vault's local folder (`backups/systemd-unit-path` under `.wiki-island/local` in git mode, the device data folder in folder mode), so a crash or a changed `XDG_CONFIG_HOME` never leaves a unit that uninstall cannot find. A later successful apply at another path retires this vault's unit and enablement link at the older paths. `wi uninstall` and `wi service uninstall` remove the unit at every recorded path and at the current path, then delete the record. If the record is damaged it is moved aside as `systemd-unit-path.bad-<unix seconds>` and work continues.
- Apply and uninstall hold a per-vault lock (`wiki-island-<vault_id>.lock` next to the record), so two setups for one vault run one after the other.
- Uninstall runs `disable --now` (or `stop` when the file is already gone; a not-loaded unit is fine), removes the `default.target.wants` link when it points at this unit file, removes the file and reloads. Without a usable manager it removes the unit file and that link without calling systemctl.
- `status` reports label, installed, enabled, running and the unit path; "configured" means installed and enabled.
- Nothing enables lingering (`loginctl enable-linger`). The watcher runs while the user manager runs, normally from login to the end of the last session; if lingering is already enabled for the account, the watcher also runs while the owner is logged out.
- Without a systemd user session (for example a container, WSL without systemd, or a shell without a user bus), `wi setup` still finishes, skips the service and says to run `wi watch`. The same happens when the manager disappears after setup's first check; `wi doctor` reports the same as one sentence; `wi service install` and `status` return that sentence as an error.

### Windows (Task Scheduler)

- Task `wiki-island-<vault_id>` in the root folder of the current user's Task Scheduler library. It is registered with `schtasks /Create /XML <file> /TN <task> /F` from a temporary UTF-16 definition file, which is removed afterwards. No administrator rights are needed: the task belongs to the current user (`UserId` is the SID that `whoami /user` reports), runs with that user's interactive token (`LogonType` InteractiveToken) and `RunLevel` LeastPrivilege, and starts at that user's logon (`LogonTrigger`).
- The action runs `<absolute wi binary> watch --vault "<absolute vault root>"` with the vault as working folder. The vault argument is quoted for the Windows command-line parser and every value is XML-escaped; a program path with a space is quoted; a `\\?\` prefix from a canonical path is dropped. Task Scheduler expands `%NAME%` references in the program, arguments and working folder, so planning refuses a program or vault path that contains `%` with one sentence.
- Settings: `ExecutionTimeLimit` PT0S (no time limit), `DisallowStartIfOnBatteries` and `StopIfGoingOnBatteries` false, `MultipleInstancesPolicy` IgnoreNew (a second start while running does nothing), `RestartOnFailure` every minute up to 999 times, hidden. The task runs only while the owner is logged on; there is no logged-out operation.
- Ownership marker: `<RegistrationInfo>` holds `<Source>wiki-island</Source>` and `<Description>Managed by wiki-island. Vault <vault_id>.</Description>`. `<Version>` is a 16-hex revision derived from the rest of the definition; an exported task with the same revision that is running is left alone. A task whose description is exactly `Managed by wiki-island. Vault <vault_id>. Revision <16 hex>.` without a source, the form earlier definitions carried, is also ours and is re-registered with the current definition on the next `wi setup`, so existing installs keep working.
- Presence is read from the list of all tasks (`/Query /FO CSV /NH`, exact name `\wiki-island-<vault_id>`, case-insensitive), then the definition from `/Query /TN <task> /XML`, and running from `/Query /TN <task> /FO CSV /V /NH`: the Status column is `Running`, or the Last Result column is 267009 (`SCHED_S_TASK_RUNNING`), which is numeric in every display language. A failed query is never read as "absent" or "stopped": applying and uninstalling stop before any change ("Task Scheduler did not report the background task, so nothing was changed; try again in a moment"), and `wi doctor` says background care could not be checked.
- A task with that name without both marker values belongs to someone else: applying and uninstalling refuse it with one sentence ("A scheduled task named wiki-island-<vault_id> already exists and was not created by wiki-island; rename or remove it in Task Scheduler, then run wi setup again"), `wi service status` reports that a different task with this name exists, and `wi doctor` warns that background care is not running and says to rename or remove that task.
- Applying a changed definition while the watcher runs first ends it (`/End`) and waits up to 10 s until it reports stopped; IgnoreNew would otherwise keep the old watcher. If `/End` fails or the watcher keeps running, applying stops before registering and restarts what it ended. It then registers the definition and starts the task (`/Run`) so the watcher runs now, not only at the next logon. A failure undoes only the steps already taken, newest first: the previous definition is registered again (or a new task deleted) and a watcher ended for the update is started again; the first error is reported.
- Uninstall ends a running watcher and waits until it stops, because deleting a task does not end its running instance, then deletes the task (`/Delete /F`). If the watcher does not stop, the task is kept and uninstall says so in one sentence, so running it again retries; without a task it reports nothing to remove.
- `status` reports label, installed ("configured"), running, the task name and `foreign` (a task with this name that is not ours).
- Task Scheduler is usable when `schtasks /Query /FO CSV /NH` succeeds. When it is turned off (for example by a group policy that disables the Task Scheduler service), `wi setup` still finishes, skips the service and says to run `wi watch`; `wi doctor` says the same in one sentence; `wi service install` and `status` return it as an error. `wi uninstall` changes nothing then and says to try again, because a scheduler that does not answer could still hold the task. Turning Task Scheduler back on and running `wi setup` again registers the task. `WI_SCHTASKS` replaces the `schtasks.exe` executable; tests use a fake.

### Doctor and binaries

- `wi doctor` says in plain words whether the background service runs (macOS: loaded; Linux: enabled and active; Windows: registered and running), reports no warning for a work request already converted, and its help names `~/wiki-island` as the default notes folder.
- The installer refuses a development binary: a Cargo `CACHEDIR.TAG` or `.rustc_info.json` among up to four canonical executable ancestors (custom `CARGO_TARGET_DIR` included). `--allow-dev-binary` overrides. `wi setup` uses the path it was invoked by, so a package-manager symlink stays the service binary; on Linux and Windows `wi service install` does the same.

## Install and release

`scripts/install.sh` installs `wi` and `wiki-island` into `~/.cargo/bin` on macOS and Linux, then runs `wi setup`. It needs no administrator rights and is safe to run again. It works from a clone or piped into `sh`; without a checkout it clones the repository's default branch with `--depth 1` when it must build from source. To read the source first, run `git clone https://github.com/takealook97/wiki-island.git` and then `sh wiki-island/scripts/install.sh`. After a successful install it adds `~/.cargo/bin` to the shell startup file once, so new terminals find `wi`, and runs `wi setup`.

- **Release assets.** A release holds `wiki-island-<tag>-<target>.tar.gz` for `aarch64-apple-darwin`, `x86_64-apple-darwin`, `aarch64-unknown-linux-gnu` and `x86_64-unknown-linux-gnu`, a `.zip` named `wiki-island-<tag>-x86_64-pc-windows-msvc.zip`, and `SHA256SUMS`. A tar archive holds exactly `wi`, `wiki-island`, `LICENSE` and `README.md` as regular files (`.github/workflows/release.yml`, `scripts/install.sh` `check_archive`). `scripts/install.sh` does not install the Windows archive; `scripts/install.ps1` does ([Windows installer](#windows-installer)).
- **Verification.** The installer finds the latest tag through the redirect of `releases/latest`, downloads the archive and `SHA256SUMS` over https, and requires exactly one well-formed line for the archive in `SHA256SUMS` and a matching SHA-256 digest. A mismatch or a damaged list stops the install with nothing changed and no source build. The archive may be at most 256 MiB and `SHA256SUMS` at most 64 KiB (unmeasured policy values); a larger download stops the install with nothing changed and no source build. Both programs must run (`--version`) before anything is replaced.
- **Replacement.** Both programs are replaced or neither: each new copy is staged next to its target, existing programs are backed up by copying, and each program is replaced by one rename. A failure or an interrupt restores the previous pair; if that cannot be done the installer says the installation is incomplete.
- **Source-build fallback.** The installer builds from source (`cargo install --path crates/wi-cli --locked`, installing the Rust toolchain through rustup when `cargo` is missing) when no release is published, GitHub cannot be reached, the release has no archive for this computer or no `SHA256SUMS`, `curl` or a checksum tool is missing, or a downloaded program does not run. A source build installs the Rust toolchain through rustup if needed, which takes a few minutes the first time, and needs git and a C compiler (Apple's command line tools on macOS, for example `build-essential` on Linux); when one is missing the installer says which and what to run.
- **Variables.** `WI_INSTALL_FROM_SOURCE=1` skips the download. `WI_INSTALL_BASE_URL` replaces the repository URL downloads come from; with it http is also accepted. Tests use both; `WI_INSTALL_SOURCE_CMD` replaces the source build in tests. `WI_INSTALL_MAX_ASSET_BYTES` only lowers the archive limit, for tests.
- **glibc.** The Linux archives are built on `ubuntu-22.04` and `ubuntu-22.04-arm`; the release workflow logs the highest `GLIBC_` symbol version of each program, which is 2.34. Older systems are not detected by the installer: a program that cannot run is caught by the `--version` check and falls back to the source build.
- **Requirements.** macOS on Apple silicon is the tested platform. The prebuilt Linux programs need glibc 2.34 or newer, measured on the Ubuntu 22.04 build machines; older systems build from source. Linux is tested on GitHub Actions (Ubuntu) and in an arm64 container; bare-metal Linux is untested ([VALIDATION](VALIDATION.md#platform)). Notion token storage uses the macOS keychain or Windows Credential Manager, so `wi publish notion setup` is unavailable on Linux. Git remote sync (`wi sync`) uses the `git` program on the path. Windows requirements are in [Windows](#windows).
- **Service.** `wi setup` starts the background service for the system in use: [macOS](#macos-launchd), [Linux](#linux-systemd-user-unit), [Windows](#windows-task-scheduler). Without a usable service manager setup still finishes, skips the service and says to run `wi watch`. Saving and searching through the AI never depend on the service.
- **Release process.** Pushing a `v*` tag builds the five targets, writes `SHA256SUMS` and publishes the GitHub Release; a manual run of the workflow builds the same archives as artifacts and publishes nothing ([CONTRIBUTING](../CONTRIBUTING.md#releases)). Tests: [VALIDATION](VALIDATION.md#installer-and-release).

### Windows installer

`scripts/install.ps1` installs `wi.exe` and `wiki-island.exe` on x86_64 (AMD64) Windows, then runs `wi setup`. It runs on Windows PowerShell 5.1 and PowerShell 7, needs no administrator rights and asks nothing. One line in PowerShell:

```powershell
irm https://raw.githubusercontent.com/takealook97/wiki-island/main/scripts/install.ps1 | iex
```

- **Architecture.** Any processor architecture other than AMD64 stops with one plain sentence before any download or write.
- **Download.** It finds the latest tag through the redirect of `<base>/releases/latest`, then downloads `wiki-island-<tag>-x86_64-pc-windows-msvc.zip` and `SHA256SUMS` from `<base>/releases/download/<tag>/`. It applies the `SHA256SUMS` rules of `scripts/install.sh` (exactly one well-formed line for the archive; CRLF line ends, an upper-case digest and a `*` marker are accepted). A mismatch or a damaged list stops the install with nothing changed. The archive may be at most 256 MiB and `SHA256SUMS` at most 64 KiB (unmeasured policy values); a larger download stops the install with nothing changed. Received bytes are counted, so a missing or false `Content-Length` cannot get past the limit.
- **Archive check.** The archive must hold exactly `wi.exe`, `wiki-island.exe`, `LICENSE` and `README.md` as files at its root; an optional `./` prefix is accepted. A folder entry, a duplicate, a `..` component, an absolute or drive-qualified name, any other entry, or an entry whose Unix file type is not a regular file (for example a symbolic link) stops the install before anything is extracted. Only the two programs are copied out, one entry at a time, into a new staging folder next to the program folder; there is no whole-archive extract.
- **Folders.** Programs go to `%LOCALAPPDATA%\Programs\wiki-island\bin`; staging is `%LOCALAPPDATA%\Programs\wiki-island\.bin-stage-<id>`. If the program folder or any existing folder above it, up to the drive root, is a link (junction or symbolic link), the installer stops before it reads, writes or removes anything there and says which folder is a link; it checks again after the download and right before placing the programs. A file or folder in the way of a program stops the install before any change.
- **Replacement.** Each new program must run `--version` from staging before anything is replaced. An existing program is renamed aside and the new one moved in, so a running `wi.exe` does not block the install. A failure or Ctrl+C puts the older pair back; if that cannot be done the installer says the installation is incomplete and to run it again. Renamed older copies are removed at the end of the run, and any that could not be removed (a running `wi.exe`) at the start of the next run.
- **Path.** The program folder is added once to the user `Path` in the registry (`HKCU:\Environment`). The stored text and value kind are kept, so `%USERPROFILE%`-style references in an existing `REG_EXPAND_SZ` value stay unexpanded, and nothing is written when the entry is already there (case-insensitive, a trailing `\` ignored). New terminal windows find `wi`, and the PowerShell window that ran the installer does too. If the folder name contains `;` or `%`, the programs are installed and `wi setup` runs, but the user `Path` is not changed, and the installer says so and where `wi` is.
- **Setup.** `wi setup` runs through the full path of the installed `wi.exe`, never whichever `wi` comes first on `Path`. A failing setup is reported as installed but not set up, with the advice to run `wi setup` again.
- **No source build.** With no release, no Windows archive or an unsupported architecture, the installer stops with one sentence that points to the [README](../README.md#windows) and changes nothing.
- **Rerun.** A second run installs the latest release over the current pair, leaves `Path` unchanged when the entry is present and runs `wi setup` again.
- **Piped use.** The script is safe to pipe into `iex`: it never calls `exit`, so a failure prints one sentence and ends with a terminating error, and the calling PowerShell window stays open. It enables TLS 1.2 explicitly for Windows PowerShell 5.1.
- **Variables.** `WI_INSTALL_BASE_URL` replaces the repository URL downloads come from; with it http is also accepted. `WI_DEBUG=1` prints the details of an unexpected error. Test hooks: `WI_INSTALL_DIR` (program folder), `WI_INSTALL_SKIP_SETUP=1` (skip `wi setup`), `WI_INSTALL_ARCH` (replaces the detected architecture), `WI_INSTALL_MAX_ASSET_BYTES` (only lowers the archive limit) and `WI_INSTALL_TEST_FAIL` (comma-separated replacement steps that fail on purpose: `aside:<program>`, `place:<program>`, `restore:<program>`).
- **Removal.** `wi uninstall` removes the service and the app connections and keeps the notes. Then delete the folder `%LOCALAPPDATA%\Programs\wiki-island` and remove its `bin` entry from the user `Path` (Settings, "Edit environment variables for your account"). There is no Windows uninstall script; the `cargo uninstall` hint of `scripts/uninstall.sh` does not apply to this install.
- **Tests.** [VALIDATION](VALIDATION.md#installer-and-release).

### Build from source on Windows

Install [rustup](https://rustup.rs) with the MSVC toolchain, which needs the Visual Studio Build Tools "Desktop development with C++" workload, then build in a terminal (the repository pins the Rust version):

```powershell
git clone https://github.com/takealook97/wiki-island.git
cd wiki-island
cargo install --path crates/wi-cli --locked
wi setup
```

`wi setup` creates the notes folder (`%USERPROFILE%\wiki-island`), connects the AI apps it finds and runs the first maintenance pass. The per-device data (history for synced folders, index state, backups) is in `%LOCALAPPDATA%\wiki-island`. It also registers a Task Scheduler task for the current user that runs `wi watch` at each logon and starts it now ([Windows (Task Scheduler)](#windows-task-scheduler)). This needs no administrator rights.

## Recovery of a single path

A recovery problem on one path (unreadable, non-UTF-8, unexpected kind, rename failure) becomes a work request and a `wi doctor` problem, and recovery continues with the other intents. `Vault::open` does not fail because of one intent's path. A manifest, lock or corruption error still fails the open.

- **Held intent.** A file-system error on one of an open intent's own paths records one `recovery-problem` work request per sequence id and path and leaves the intent open. Maintenance and the next write to the path retry it.
- **Unexpected entry kinds.** An engine scratch name (`.wi-tmp-`, `.wi-conflict-`, `.wi-moved-`) that is not a regular file (directory, FIFO, symlink, other) is never treated as absent: recovery records one `recovery-problem` for (seq, path) and holds the intent; `wi doctor` reports such entries by name, of every kind, without following symlinks.
- **Held intents block only their own paths.** Several intents may be open when their paths are disjoint. A write, edit, move, revert or import that touches a held path first retries recovery once, then fails fast with `recovery-held`, naming the path and the sequence id of its work request. Other paths proceed. Watcher and `wi commit` ingress skip a held path. The flush commits later records out of sequence order and retires only up to the held sequence id; a held member of a bulk-import batch still stops the flush. `wi doctor` lists the held paths.
- **No unlinking of unread bytes.** A displaced temp whose bytes cannot be read is renamed to its conflict copy (a rename needs no read permission) with a `conflict-copy` request noting it was unread; if that fails, the temp is kept with a `recovery-problem` request. `wi commit`'s dead-pid temp cleanup skips a temp named by a `recovery-problem` request or belonging to a held intent.
- **Conflict-copy names.** A copy is `.<name>.wi-conflict-<seq>`; when taken, `-2`, `-3`, … is appended. Opening the vault records a missing `conflict-copy` request for any existing copy of an open intent's target or move source. `wi doctor` warns (`conflict-copies`) about any copy no request names.
- **Move sources.** An aside (`.<name>.wi-moved-<seq>`) is always settled at open: removed when it still derives the moved bytes, otherwise kept as a conflict copy; when the move was undone it is always kept as a conflict copy. The live source name is settled only when the destination holds the moved bytes, and it is renamed aside before it is read, so an editor's atomic save there is never removed.
- **Crash cleanup at open.** Under the lock, for an open intent: temp files holding the old or new bytes are removed, any other bytes become a conflict copy; a completed move's source is removed when it still has the moved bytes. A temp file of a writer killed before its intent is removed by `wi commit` once its pid is gone.
